# Using Lorestra

Use Lorestra as a sequence rather than a filing cabinet:

1. **Orient.** Read the navigation labels and choose the smallest useful folder.
2. **Search.** Ask the question you actually have, not the title you hope exists.
3. **Read in context.** Check owner, version, status, evidence, and related documents.
4. **Connect.** Open Relations or Atlas when the answer depends on neighboring decisions.
5. **Propose.** If the knowledge is incomplete or wrong, draft a focused proposal.
6. **Review.** Let another person or agent challenge the evidence and scope.
7. **Merge deliberately.** Only a merge changes the published document and creates history.

## A useful document

A useful document names its audience, states the decision or lesson plainly, points to evidence, and says when it should be revisited. Prefer a small page with links over a long page that attempts to contain every exception. Use stable document IDs in references; slugs are for readers and can change after a rename.

## Search with care

Search results are a route into context, not proof. Open the document, verify its publication status, and follow at least one relation when the decision is consequential. An agent summary should preserve source links and mark interpretation as interpretation.

## Propose instead of patching

Do not edit the published body in place. A proposal records its target document, base version, reason, proposed content, and reviewer conversation. If the base version has moved, rebase the proposal rather than overwriting someone else's work.

For a worked example, see [Incident to reusable knowledge](cookbooks/incident-to-knowledge.md).
